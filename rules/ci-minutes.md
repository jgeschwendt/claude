# Actions minutes

- **Private repos spend as few GitHub Actions minutes as possible.** Minutes on a private repo are metered, macOS at ten times the rate, and the account hit its limit on 2026-10-21 with bifrost's macOS job. A private repo's `ci.yaml` runs on `workflow_dispatch` only, never on push or pull_request; release artifacts build on this machine, and a release workflow runs on `workflow_dispatch` only, never on a tag push. The gates run on this machine, and a merge goes through floodgate, the local merge queue (`jgeschwendt/floodgate`, its daemon `dev.gigantic.floodgate`, its page on 127.0.0.1:1709): never open or merge a PR on a private repo expecting the cloud to gate it. Public repos keep their CI, and so do private repos in a paid org with its own minutes (imcs-solutions): their workflows keep push and pull_request triggers and their rulesets' required checks; the rule is for jgeschwendt's own private repos. (paid-org carve-out since 2026-11-02 · imcs#104: "revert for imcs this is a paid org, it has minutes to use")
- **To queue a PR, `floodgate add jgeschwendt/<repo>#<n>`** after review; the add is the admitting act and work starts at once, so a shift adds its own PR once its review step passes, and a PR nobody added never merges. floodgate puts the `queue` label on the PR as a mark and removes it when the PR lands or bounces; labelling by hand admits nothing, because nothing polls GitHub. Each repo has a line: every PR's candidate is built on the one ahead of it and gated at once (`mise run check` where the repo defines it, else `hk run pre-push`, else red "no gate"); a green head rebase-merges, a red one gets the gate's tail as a PR comment and leaves the line, and the PRs behind it are rebuilt without it. After the fix, add it again (or requeue from the page). `floodgate status` shows the lines. A repo joining the queue gets a root `check` mise task first. - **A private tool installs from a local build, never a release.** `mise run install` in the checkout builds, stamps the version, puts the binary on a stable path and runs the tool's `setup`; run it again to upgrade. No GitHub release, signing workflow, hotswap or `upgrade` verb: a release is for a tool another machine installs without building (public repos, through hotswap).
